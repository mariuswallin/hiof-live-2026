src/worker.tsx

worker.tsxInngang

Startpunktet for hele appen. defineApp er en liste som leses ovenfra og ned for hver forespørsel: først felles headere (setCommonHeaders), så API-rutene fra taskRoutes, så /api/status, og til slutt sidene som vises inni Document: /, /tasks og /tasks-client.

Bruker: task-routes.ts, pages/TasksPage.tsx, pages/TasksPageClient.tsx

src/features/

Alt som handler om oppgaver. Filene på toppnivå er lagene; undermappene er sider, komponenter og hjelpere.

task-routes.tsMottak

Oversikten over API-et. Kobler URL og HTTP-metode til riktig funksjon i controlleren: GET/POST på /api/v1/tasks, GET/PUT/DELETE på /api/v1/tasks/:id og POST på /api/v1/tasks/:id/:action. Her kan mellomvare som requireUser legges inn senere.

Bruker: task-controller.ts

task-controller.tsMottak

Oversetter mellom HTTP og resten av appen. Leser det som kommer inn (query-parametre, JSON-body), kaller service, og gjør svaret om til en Response med statuskode: 200 for listen, 201 for ny oppgave, og ellers koden fra feilen (400 eller 500).

Bruker: task-service.ts, utils/parse-params.ts

actions.tsMottak

Server action ("use server"). Skjemaet i nettleseren kaller createTaskAction som om den var en vanlig funksjon, og React sender kallet som en POST til serveren. Funksjonen leser title og dueDate fra FormData, kaller service.create og sender tilbake enten den nye oppgaven, eller feilene sammen med det brukeren skrev.

Bruker: task-service.ts, lib/demo-chaos.ts

task-api.tsNettleser

Kode for nettleseren som snakker med REST-API-et. listTasks() henter oppgaver og createTask() lager en ny, begge med fetch. Hvis serveren ikke svarer, gir listTasks tilbake et vanlig { ok: false }-svar i stedet for å krasje.

Bruker: fetch mot /api/v1/tasks

task-service.tsLogikk

Hjernen. Her ligger reglene for oppgaver: sjekk at input har riktig form, sjekk reglene, be repository om data, og gjør databaseradene om til DTO-er. Filen vet ingenting om HTTP eller SQL. Derfor kan alle tre inngangene bruke den.

Bruker: task-repository.ts, task-schema.ts, task-mapper.ts, utils/validate-task.ts, utils/validate-list-params.ts

task-schema.tsLogikk

Zod-skjemaet for input. Beskriver hva en ny oppgave kan inneholde: title (tekst, trimmes), completed (valgfri) og dueDate (gjøres om fra tekst til Date). updateTaskSchema er det samme, bare med alle felt valgfrie.

Ikke å forveksle med db/schema/task-schema.ts, som beskriver tabellen.

task-mapper.tsLogikk

toTaskDTO gjør en databaserad om til det klienten skal se. Den tar med id, title, completed, dueDate og createdAt (som tekst), og lar userId bli igjen på serveren. TaskDTO-typen brukes av sidene og komponentene.

Bruker: Task-typen fra db/schema

task-repository.tsDatatilgang

Det eneste stedet i features/ som snakker med databasen. findMany filtrerer på completed, søker i tittelen med q, sorterer nyeste først og begrenser med limit. create setter inn en rad og får den tilbake. Databasefeil fanges og blir til { ok: false, code: "500" }.

Bruker: db fra db/index.ts, tasks-tabellen fra db/schema

src/features/pages/

TasksPage.tsxMottak

Serverkomponent for /tasks. Henter oppgavene direkte fra service, uten fetch, fordi koden allerede kjører på serveren. Mens den venter, viser Suspense et skjelett. Går noe galt, vises feilmeldingen; ellers TaskList.

Bruker: task-service.ts, utils/parse-params.ts, components/TaskList.tsx

TasksPageClient.tsxNettleser

Klientkomponent for /tasks-client. Viser den andre måten å hente data på: siden kommer tom, og useEffect henter oppgavene via task-api.ts etterpå. Fin å sammenligne med TasksPage.

Bruker: task-api.ts

src/features/components/

TaskList.tsxNettleser

Viser skjemaet for ny oppgave og én TaskItem per oppgave. Sender createTaskAction videre til skjemaet som prop.

Bruker: CreateTaskForm.tsx, TaskItem.tsx, actions.ts

CreateTaskForm.tsxNettleser

Skjemaet «Ny oppgave». useActionState kjører server action og tar vare på svaret: isPending gir «Lagrer…» på knappen, og feltfeil for title og dueDate vises under feltene. Ved feil fylles feltene inn igjen med det brukeren skrev.

TaskItem.tsxNettleser

Én rad i listen: avkrysningsboks, tittel (gjennomstreket når den er ferdig), frist og Slett-knapp.

src/features/utils/

parse-params.tsMottak

Gjør ?completed=true&q=melk om til { completed: "true", q: "melk" }. Alt er fortsatt tekst; sjekken skjer i service.

validate-list-params.tsLogikk

Sjekker og gjør om listeparametrene: completed må være "true" eller "false" og blir en boolean, q trimmes, og limit blir et tall med øvre grense LIST_LIMIT_MAX (100). Ved feil svarer den med hvilket felt som er galt.

validate-task.tsLogikk

Reglene for en oppgave: tittelen kan ikke være tom eller lengre enn 200 tegn, og fristen kan ikke være før i dag (norsk tid, Europe/Oslo).

Bruker: date.ts

date.tsLogikk

Dato-hjelpere. startOfToday finner midnatt i dag i norsk tid, defaultDueDate gir en dato én uke frem.

src/db/

Alt om selve databasen. Ingen regler for oppgaver her, bare hvordan dataene ser ut og hvordan vi kobler til.

index.tsDatabase

Lager databaseklienten. drizzle(env.DB, { relations }) kobler Drizzle til D1-databasen som heter DB i wrangler.jsonc. Eksporterer db, som repository bruker, og typen DB.

Bruker: schema/, relations.ts

relations.tsDatabase

Forteller Drizzle hvordan tabellene henger sammen: en bruker har mange oppgaver, og en oppgave har én bruker. Gjør at db.query kan hente relaterte rader.

seed.tsDatabase

Testdata. Tømmer tabellene og legger inn brukeren «Test Testesen» med to oppgaver. Kjøres med npm run seed, ikke av appen selv.

src/db/schema/

task-schema.tsDatabase

Beskriver tasks-tabellen i TypeScript: id (lages med nanoid), title, completed, due_date, user_id (peker på en bruker og slettes sammen med den) og created_at. Gir også typene Task, CreateTask og UpdateTask som resten av appen bruker.

Bruker: user-schema.ts, lib/id.ts

user-schema.tsDatabase

users-tabellen: id (teller oppover), name og email (må være unik). Typene User og CreateUser.

index.tsDatabase

Samler tabellene i én import, så andre filer kan skrive import { tasks } from "@/db/schema".

Utenfor de tre mappene: lib/id.ts lager id-er til tasks-tabellen. lib/demo-chaos.ts legger på kunstig ventetid i dev, så du rekker å se skjelett og «Lagrer…».

drizzle/migrations/ er SQL generert fra schema-filene med npm run migrate:new. Det er den som faktisk lager tabellene i D1 når du kjører npm run migrate:dev.

En ny oppgave, steg for steg

Slik ser dataene ut i hvert lag når noen sender POST /api/v1/tasks. Legg merke til at formen endrer seg litt for hver fil.

  1. klienten

    Sender en forespørsel med JSON. Det kan være task-api.ts, Postman eller curl.

    POST /api/v1/tasks
{ "title": "  Kjøpe melk ", "dueDate": "2026-10-10" }
  2. task-routes.ts

    worker.tsx går gjennom rutene. Den første som passer er /api/v1/tasks med post.

    route("/api/v1/tasks", { post: controller.create })
  3. task-controller.ts

    Leser body. Controlleren vet ikke om dataene er gyldige, og det er heller ikke dens jobb.

    const body = await request.json(); // unknown
await service.create(body);
  4. task-schema.ts

    Service kjører zod-skjemaet. Tittelen trimmes og datoteksten blir en ekte dato.

    { title: "Kjøpe melk", dueDate: Date(2026-10-10) }
  5. validate-task.ts

    Reglene sjekkes: ikke tom, maks 200 tegn, frist ikke i fortiden. Så legger service til userId (fast 1 til innlogging er på plass).

    { title: "Kjøpe melk", dueDate: Date(…), userId: 1 }
  6. task-repository.ts

    Setter inn raden og ber om å få den tilbake.

    db.insert(tasks).values(data).returning().get()
  7. db/ + D1

    Drizzle fyller inn id og createdAt fra schema-filen, D1 setter completed til false, og hele raden kommer tilbake.

    { id: "V1StGXR8_Z5jdHi6B-myT", title: "Kjøpe melk",
  completed: false, dueDate: Date(…), userId: 1,
  createdAt: Date(…) }
  8. task-mapper.ts

    Raden blir en DTO. userId blir igjen på serveren, og createdAt blir tekst.

    { id, title, completed: false, dueDate,
  createdAt: "2026-10-07T10:41:25.000Z" }
  9. task-controller.ts

    Svaret pakkes inn og sendes tilbake med status 201.

    201 Created
{ "ok": true, "data": { "id": "V1StGXR8_Z5jdHi6B-myT", … } }

Hvis tittelen er tom

Da stopper det i steg 5. validate-task.ts sier nei, service lager et feilsvar med kode "400", og controlleren bruker koden som HTTP-status. Repository og databasen blir aldri spurt.

400 Bad Request
{ "ok": false, "error": {
    "code": "400", "message": "Ikke gyldig data",
    "fieldErrors": { "title": ["Tittel kan ikke være tom"] } } }

To mønstre som går igjen

Når du har skjønt disse to, kan du lese alle filene i features/.

Hvert lag får laget under seg som argument

Nederst i hver fil lages laget med en create…-funksjon, og laget under sendes inn:

// task-repository.ts
export const repository = createTaskRepository(db);
// task-service.ts
export const service = createTaskService(repository);
// task-controller.ts
export const controller = createTaskController(service);

I appen sendes den ekte D1-databasen inn. I testene sendes en SQLite-database i minnet inn i stedet. Service-koden er helt lik, så testene sjekker de ekte reglene uten Cloudflare.

// __tests__/task-service.test.ts
db = drizzle({ client: new Database(":memory:"), relations });
service = createTaskService(createTaskRepository(db));

Alle lag svarer med samme form

Ingen lag kaster feil oppover. Alle svarer med enten suksess eller en beskrevet feil:

| { ok: true;  data: TaskDTO }
| { ok: false; error: {
      code: "400" | "500";
      message: string;
      fieldErrors: Record<string, string[]> } }

Repository fanger databasefeil og gir "500". Service gir "400" for ugyldig input. Controlleren gjør code om til HTTP-status, mens TasksPage og skjemaet viser message og fieldErrors til brukeren.

Hvert lag sjekker if (!result.ok) return result; og sender feilen videre uendret.

Ikke ferdig ennå

  • find, update, remove og action finnes i rutene, men controller, service og repository returnerer bare null. Rutene på /api/v1/tasks/:id gir derfor ikke et gyldig svar foreløpig.
  • Slett-knappen i TaskItem logger bare til konsollen, og avkrysningsboksen er ikke koblet til noe.
  • userId er fast satt til 1 til innlogging er på plass.
