En ny oppgave, steg for steg

Slik ser dataene ut i hvert lag når noen sender POST /api/v1/tasks. Legg merke til at formen endrer seg litt for hver fil.

  1. klienten

    Sender en forespørsel med JSON. Det kan være task-api.ts, Postman eller curl.

    POST /api/v1/tasks
{ "title": "  Kjøpe melk ", "dueDate": "2026-10-10" }
  2. task-routes.ts

    worker.tsx går gjennom rutene. Den første som passer er /api/v1/tasks med post.

    route("/api/v1/tasks", { post: controller.create })
  3. task-controller.ts

    Leser body. Controlleren vet ikke om dataene er gyldige, og det er heller ikke dens jobb.

    const body = await request.json(); // unknown
await service.create(body);
  4. task-schema.ts

    Service kjører zod-skjemaet. Tittelen trimmes og datoteksten blir en ekte dato.

    { title: "Kjøpe melk", dueDate: Date(2026-10-10) }
  5. validate-task.ts

    Reglene sjekkes: ikke tom, maks 200 tegn, frist ikke i fortiden. Så legger service til userId (fast 1 til innlogging er på plass).

    { title: "Kjøpe melk", dueDate: Date(…), userId: 1 }
  6. task-repository.ts

    Setter inn raden og ber om å få den tilbake.

    db.insert(tasks).values(data).returning().get()
  7. db/ + D1

    Drizzle fyller inn id og createdAt fra schema-filen, D1 setter completed til false, og hele raden kommer tilbake.

    { id: "V1StGXR8_Z5jdHi6B-myT", title: "Kjøpe melk",
  completed: false, dueDate: Date(…), userId: 1,
  createdAt: Date(…) }
  8. task-mapper.ts

    Raden blir en DTO. userId blir igjen på serveren, og createdAt blir tekst.

    { id, title, completed: false, dueDate,
  createdAt: "2026-10-07T10:41:25.000Z" }
  9. task-controller.ts

    Svaret pakkes inn og sendes tilbake med status 201.

    201 Created
{ "ok": true, "data": { "id": "V1StGXR8_Z5jdHi6B-myT", … } }

Hvis tittelen er tom

Da stopper det i steg 5. validate-task.ts sier nei, service lager et feilsvar med kode "400", og controlleren bruker koden som HTTP-status. Repository og databasen blir aldri spurt.

400 Bad Request
{ "ok": false, "error": {
    "code": "400", "message": "Ikke gyldig data",
    "fieldErrors": { "title": ["Tittel kan ikke være tom"] } } }

Krysse av og slette, steg for steg

To endringer på samme rad, to forskjellige veier inn. Avkrysningen bruker en server action, slettingen bruker fetch mot REST-API-et. Fra service og ned er veien den samme.

Krysse av: toggleTaskCompleted

  1. TaskItem.tsx

    Brukeren krysser av. useTransition låser boksen og viser «lagrer…» til svaret kommer.

    startTransition(async () => {
  const result = await toggleTaskCompleted(id, !completed);
  if (!result.ok) setError(result.error);
});
  2. actions.ts

    Server action. Kjører på serveren og sender bare det ene feltet som skal endres.

    await service.update("V1StGXR8_Z5jdHi6B-myT",
  { completed: true });
  3. task-schema.ts

    updateTaskSchema har alle felt valgfrie, så ett felt holder. Et tomt objekt stopper service selv, med 400 «Ingen felt å oppdatere».

    updateTaskSchema.safeParse({ completed: true })
// { completed: true }
  4. validate-task.ts

    Samme regler som for en ny oppgave, men bare for feltene som er med. Her er verken title eller dueDate med, så alt er greit.

    validateTask({ completed: true })
// { ok: true }
  5. task-repository.ts

    Endrer raden og ber om å få den tilbake. Treffer ikke id-en noen rad, blir data null.

    db.update(tasks).set(data)
  .where(eq(tasks.id, id)).returning().get()
  6. task-mapper.ts

    Raden blir en DTO, og svaret går tilbake gjennom actions.ts til TaskItem.

    { ok: true, data: { id, title: "Kjøpe melk",
    completed: true, dueDate, createdAt } }
  7. TaskItem.tsx

    Etter en server action rendrer rwsdk siden på nytt. Raden får oppgaven som prop med ny verdi, og tittelen blir gjennomstreket.

    <input type="checkbox" checked={completed} />
// completed === true, fra serveren

Slette: DELETE /api/v1/tasks/:id

  1. TaskItem.tsx

    Slett-knappen kaller onDelete, som raden har fått som prop fra TaskList.

    startTransition(() => onDelete(id));
  2. task-api.ts

    TaskList kaller removeTask(id), som sender forespørselen. Ingen body, id-en står i URL-en.

    DELETE /api/v1/tasks/V1StGXR8_Z5jdHi6B-myT
  3. task-routes.ts

    Ruten med :id passer, og metoden velger funksjonen i controlleren.

    route("/api/v1/tasks/:id", { delete: controller.remove })
  4. task-controller.ts

    Henter id-en fra URL-en og sender den videre.

    await service.remove(params.id);
  5. task-service.ts

    Sjekker først at oppgaven finnes. Finnes den ikke, stopper det her med 404.

    await repository.findById(id)
// { ok: true, data: { id, title, … } }
  6. task-repository.ts

    Sletter raden. Det er ingenting å sende tilbake.

    db.delete(tasks).where(eq(tasks.id, id))
// { ok: true }
  7. task-controller.ts

    Svarer 204: det gikk bra, og svaret har ingen body.

    204 No Content
  8. TaskList.tsx

    removeTask gjør 204 om til { ok: true }. Da ber TaskList om siden på nytt, og raden er borte.

    await navigate(window.location.pathname, {
  history: "replace", info: { scrollToTop: false } });

Hvis oppgaven ikke finnes

Begge veiene ender i samme svar fra service, med kode "404". Ved oppdatering oppdages det etter at repository har prøvd (ingen rad kom tilbake), ved sletting før (findById ga null). Controlleren bruker koden som HTTP-status. Server action sender bare meldingen videre, og TaskItem viser den under raden.

404 Not Found
{ "ok": false, "error": {
    "code": "404", "message": "Task finnes ikke",
    "fieldErrors": {} } }

Hvert lag får laget under seg som argument

Nederst i hver fil lages laget med en create…-funksjon, og laget under sendes inn:

// task-repository.ts
export const repository = createTaskRepository(db);
// task-service.ts
export const service = createTaskService(repository);
// task-controller.ts
export const controller = createTaskController(service);

I appen sendes den ekte D1-databasen inn. I testene sendes en SQLite-database i minnet inn i stedet. Service-koden er helt lik, så testene sjekker de ekte reglene uten Cloudflare.

db = drizzle({ client: new Database(":memory:"), relations });

Alle lag svarer med samme form

Ingen lag kaster feil oppover. Alle svarer med enten suksess eller en beskrevet feil:

| { ok: true;  data: TaskDTO }
| { ok: false; error: {
      code: "400" | "404" | "500";
      message: string;
      fieldErrors: Record<string, string[]> } }

Repository fanger databasefeil og gir "500". Service gir "400" for ugyldig input og "404" når oppgaven ikke finnes. Controlleren gjør code om til HTTP-status, mens TasksPage, skjemaet og TaskItem viser message og fieldErrors til brukeren.

Sletting har ingenting å sende tilbake. Da er suksess bare { ok: true }, uten data.

Hvert lag sjekker if (!result.ok) return result; og sender feilen videre uendret.

  • update, remove og findById har ingen tester ennå. task-service.test.ts dekker bare list.
  • userId er fast satt til 1 til innlogging er på plass.

Det som skjer før en forespørsel når features/tasks/.

Request og response (HTTP)Nettleseren sender en request, serveren svarer med en response.

Hele weben bygger på HTTP. En request har en URL, en HTTP-metode og headere. En response har en statuskode, headere og en body med innholdet: HTML, JSON eller noe annet. En dynamisk webapp lager svaret ut fra hvem som spør og hva de spør om.

REST-API

Kontrakten mellom en klient og serveren.

RESTRessursen står i URL-en, HTTP-metoden sier hva du vil gjøre med den.

REST er en arkitektonisk stil for API-er, ikke en teknologi. Kjernen er et ensartet grensesnitt: et verb (HTTP-metoden) og en ressurs (her: oppgaver). Lærer du én del av API-et, forstår du resten.

Hver forespørsel er selvstendig (stateless): den inneholder alt serveren trenger, og serveren husker ikke forrige kall. Klient og server er adskilt og snakker bare sammen gjennom API-et. REST passer når CRUD dominerer og flere klienter skal bruke det samme API-et.

I denne appen

task-routes.ts er hele REST-flaten: ressursen tasks under /api/v1/tasks, og metoden velger funksjon i task-controller.ts. task-api.ts er én klient, men Postman og curl kan bruke det samme API-et.

HTTP-metoderGET henter, POST oppretter, PATCH endrer litt, DELETE sletter.

Metodene er ikke bare teknikk, de sier hva klienten vil. GET henter data, også med søk og filtrering, og endrer ingenting. POST oppretter en ny ressurs der serveren lager id-en. PUT erstatter hele ressursen, PATCH oppdaterer deler av den. DELETE sletter.

GET og PUT er idempotente: samme kall flere ganger gir samme resultat. POST er det ikke: to kall gir to ressurser.

StatuskoderTallet i svaret som sier hvordan det gikk.

Arkitektur og lag

Hvordan serverkoden er delt opp, og hvorfor.

N-lags arkitekturKoden deles i lag med hvert sitt ansvar, og hvert lag snakker bare med laget under.

Lagene i en webapp er vanligvis controller (HTTP inn og ut), service (forretningslogikk og regler), repository (databaseoperasjoner) og databasen selv. Avhengigheten går én vei: øvre lag bruker nedre lag, aldri omvendt.

Gevinsten er at hvert lag kan testes for seg, at en endring i ett lag ikke sprer seg, og at servicen kan brukes av flere innganger: REST-API, server actions og sider.

Kurset sier også når det ikke lønner seg: en enkel CRUD-app uten særlig logikk trenger ikke nødvendigvis lagene. Webapp 2026 kaller databasen rett fra server actions for å holde eksemplene korte.

I denne appen

task-controller.ts → task-service.ts → task-repository.ts → db/index.ts. Controlleren vet ingenting om databasen, og servicen vet ingenting om HTTP. Derfor kan actions.ts og TasksPage.tsx kalle samme service som API-et.

React på serveren og i nettleseren

Hva som kjører hvor, og hvordan komponentene snakker sammen.

Server- og klientkomponenterKomponenter kjører på serveren som standard. "use client" sender dem også til nettleseren.

En serverkomponent kjøres ferdig på serveren, og nettleseren får bare resultatet som HTML. Den kan bruke async/await og hente data direkte, men ikke hooks eller klikk-hendelser. En klientkomponent sendes i tillegg som JavaScript og hydreres i nettleseren, så den kan reagere på klikk og huske tilstand.

"use client" er et fildirektiv: alt filen eksporterer og importerer, blir klientkode. En serverkomponent kan rendre en klientkomponent, men ikke omvendt. Regelen: bruk serverkomponenter så lenge du kan.
