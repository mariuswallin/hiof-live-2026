Result<T> er kontrakten

Repository, service og server actions svarer alltid med samme form. Den som kaller sjekker result.ok og vet da nøyaktig hva som ligger i data eller error. Fordi error.code er HTTP-statusen som tekst, trenger controlleren ingen oppslagstabell: Number(result.error.code) er statusen.

error.code HTTP Når UI gjør
ok: true 200 / 201 / 204 Alt gikk bra. 201 når noe ble opprettet, 204 når noe ble slettet (ingen body). Vis data eller suksessmelding
"400" 400 Ugyldig eller manglende input. fieldErrors sier hvilket felt. Vis melding ved feltet
"401" 401 Ikke innlogget Send til innlogging
"403" 403 Innlogget, men ikke din ressurs, eller feil rolle Vis «ingen tilgang»
"404" 404 Ressursen finnes ikke Vis tom tilstand
"409" 409 Duplikat, f.eks. e-posten finnes Forklar hva som kolliderer
"500" 500 Noe feilet på serveren, typisk i databasen Generell melding, logg detaljer
Lag 1 · nærmest databasen

Repository henter og lagrer data

Det eneste laget som snakker med databasen. Det vet ingenting om HTTP, cookies eller hvem som er logget inn.

Kalles av: ServiceReturnerer: Result<Project>, Result<Project[]> …
ORM / standard spørring
Drizzle-spørringene ligger her og ingen andre steder. Komponenter og controllere skriver aldri SQL.
Løst koblet
Resten av appen vet ikke om dataene kommer fra D1, Postgres eller en testdatabase. Bytter du database, endrer du bare dette laget.
Interface (kontrakt)
Et TypeScript-interface sier hvilke metoder som finnes og hva de returnerer. Servicen avhenger av interfacet, ikke av implementasjonen.
Result
Hver metode fanger egne feil med try/catch, logger dem og svarer { ok: false, error: { code: "500" } }. Ingen ukontrollerte exceptions oppover.
null er ikke en feil
Finner findById ingenting, svarer den { ok: true, data: null }. Det er servicen som bestemmer at det blir 404.
Export av factory
createProjectRepository(db) lager en ny instans. Brukes i tester der du sender inn en testdatabase.
Export av singleton
repository er én ferdig instans som resten av appen importerer.
Paginering
page og limit blir til limit og offset. Du henter aldri tusen rader for å vise tjue.
Filtrering / søk
q, status og ownerId blir til where. I Drizzle v1 er det et vanlig objekt, og undefined betyr «ikke filtrer på dette».
Sortering
sortBy og order blir til orderBy. Bare kjente feltnavn, aldri fri tekst fra brukeren. Det sjekker validateListParams i servicen.
Lag 2 · reglene

Service bestemmer hva som er lov

Forretningslogikken bor her. Servicen får brukeren som parameter i stedet for å lese cookies selv. Derfor kan samme regel brukes fra en API-rute, en server action og en test.

Kalles av: Controller, server action, RSCBruker: RepositoryReturnerer: Result<ProjectDTO>
Forretningslogikk
Hvem kan opprette prosjekt, hvem blir eier, hvem får se hva. Ingen HTTP og ingen SQL, stort sett ren TypeScript.
Bruker repository
Servicen kaller repositoryet og får et Result tilbake. En databasefeil (500) sendes rett videre. null blir til 404.
Sjekk på bruker
Er brukeren logget inn (401)? Eier brukeren prosjektet, eller er det en admin (403)? Brukeren kommer fra ctx.user, sendt inn av laget over.
Admin ser alt
I list: ownerId: isAdmin(user) ? undefined : user.id. Admin får alle prosjektene, andre bare sine egne.
Validere data (Zod)
Alt som kommer ovenfra er unknown til det er validert. safeParse gir enten gyldige data eller en feil, uten å kaste. z.flattenError gjør feilen om til fieldErrors.
Regler
Zod sjekker formen. Reglene (minst 3 tegn i tittelen) ligger i validateProject, en vanlig funksjon du kan teste uten server.
Eier settes her
ownerId hentes fra brukeren, aldri fra body. Ellers kan hvem som helst opprette prosjekter i andres navn.
DTO ut
toProjectDTO plukker ut feltene klienten skal se, og gjør datoer om til tekst. Raden fra databasen går aldri rett ut.
Interface, factory, singleton
Samme mønster som repository. createProjectService(repository) gjør det enkelt å teste med et falskt repository.
Lag 3 · HTTP inn og ut

Controller oversetter mellom HTTP og koden din

Controlleren håndterer alt som har med request og response å gjøre. Den gjør rådata om til objekter på vei inn, og svaret fra servicen om til statuskode og JSON på vei ut.

Kalles av: RuteBruker: ServiceReturnerer: Response
Request og response
Det eneste laget, utenom ruter og middleware, som kjenner Request, Response, headers og statuskoder.
Ta imot data
Leser request.json() eller søkeparametrene (parseParams), og gjør dem om til vanlige objekter servicen forstår.
Konvertering kan feile
Ødelagt JSON skal gi 400 med en forståelig melding, ikke krasje. Pakk parsingen i try/catch.
Metoder / verb
Én metode per handling: list, find, create, update, remove. Ruta bestemmer hvilken som kjøres.
Validere data
Bare at bodyen lar seg lese. Formen (Zod) og reglene sjekkes i servicen.
Result → statuskode
error.code er allerede statusen som tekst: Number(result.error.code). Ved suksess velger controlleren selv: 200, 201 (opprettet) eller 204 (slettet).
Factory og singleton
createProjectController(service) og controller. Samme mønster som lagene under.
Lag 4 · inngangen

Ruter og middleware styrer hvem som slipper inn hvor

Ruta kobler URL og HTTP-verb til riktig controllermetode. Middleware kjører før alt annet og fyller ryggsekken (ctx). Interruptors står foran handleren på én rute, og kan stoppe forespørselen tidlig.

Mottar fra: NettleserenSender videre til: Controller eller side
/api/v1/resource
Ressurser i flertall, som substantiv, på engelsk: /api/v1/projects, ikke /api/v1/getProject. v1 lar deg lage en ny versjon senere uten å knekke gamle klienter.
HTTP-metoder
GET henter, POST oppretter, PUT erstatter alt, PATCH endrer deler, DELETE sletter. Verbet står i metoden, ikke i URL-en.
Én route per sti
Samle metodene i samme route(...). rwsdk velger den første ruta som matcher stien. Står stien to ganger, svarer den første 405 på metoden den mangler.
Headers og body
Headers bærer metadata: Content-Type, Cookie, Accept. Body bærer selve dataene.
Middleware og interruptors
Middleware står øverst i defineApp og kjører på alle forespørsler (setUser). En interruptor står foran handleren på én rute (requireUser). Returnerer de ingenting, går forespørselen videre. Returnerer de en Response, stopper kjeden der.
API og sider
API-rutene står utenfor render() og svarer med JSON. Sidene står inni, og bruker requireUserPage, som sender deg til /login i stedet for å svare 401.
Response
Svaret har statuskode, headers og body. Body er { ok: true, data } ved suksess og { ok: false, error } ved feil.

Verb og URL Controller Hva skjer

På tvers av alle lag

Login-flyten: fra skjema til ctx.user

Innlogging er to ulike forespørsler. Den første setter en cookie. Alle senere forespørsler har cookien med seg, og middleware gjør den om til ctx.user før noe annet kjører.

Forenklet med vilje. Dette er jukseinnloggingen fra tasks: du velger hvem du er, uten passord, og cookien er bare bruker-id-en. Login-handleren snakker rett med databasen. En ekte innlogging har samme lagdeling som prosjektene: controller, service (passord mot hash) og repository, og lagrer en tilfeldig sesjons-id i en sessions-tabell. Stedene som er usikre er merket USIKKERT: i koden, med alternativet.

  1. UI

    Brukeren velger seg selv i nedtrekkslista og sender skjemaet: POST /login med userId som FormData. Et vanlig <form method="post">, ingen JavaScript.

  2. Middleware

    setUser finner ingen cookie og setter ctx.user = null. /login har ingen interruptor, så forespørselen går videre.

  3. Rute-handler

    login i auth-routes.ts leser FormData og sjekker at userId er et positivt heltall. Ugyldig gir 400.

  4. Database

    db.query.users.findFirst({ where: { id } }). Finnes ikke brukeren, svarer handleren 400 «Ugyldig innlogging».

  5. Rute-handler

    Svarer 303 See Other med Location: /projects og Set-Cookie. 303 betyr «hent denne siden med GET», så Reload sender ikke skjemaet på nytt.

  6. Nettleser

    Lagrer cookien og følger Location. JavaScript kan ikke lese cookien (HttpOnly), men nettleseren sender den automatisk med på alle senere forespørsler til samme domene.

Neste forespørsel, f.eks. POST /api/v1/projects

  1. Middleware

    setUser leser Cookie: session=2, slår opp brukeren i databasen og setter ctx.user = { id, name, email, role }. Rollen bor i databasen, ikke i cookien.

  2. Interruptor

    requireUser eller requireAdmin leser ctx.user. Mangler brukeren: 401. Feil rolle: 403. Ellers går forespørselen videre.

  3. Controller → Service

    Controlleren sender ctx.user inn i servicen, som bruker user.id som eier og sjekker eierskap og rolle der reglene krever det.

Anatomien til Set-Cookie

Set-Cookie: session=2; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600; Secure
session=2
Bare bruker-id-en. Ingen rolle og intet passord. USIKKERT: endrer du 2 til 1 i DevTools, er du en annen bruker. Alternativ: signer verdien, eller lagre en tilfeldig sesjons-id i en sessions-tabell.
HttpOnly
JavaScript i nettleseren kan ikke lese cookien (document.cookie). Klarer noen å kjøre kode på siden (XSS), får de ikke med seg sesjonen.
SameSite=Lax
Sendes ikke med når andre nettsteder poster skjema eller kaller fetch hit. Beskytter mot CSRF.
Path=/
Gjelder hele appen, både sider og /api.
Max-Age=3600
Sekunder før nettleseren kaster cookien: én time. 0 betyr «slett nå», og det er slik utlogging virker.
Secure
Sendes bare over HTTPS. Tasks skrur den av på utviklingsserveren, som kjører på http.

Kjeden: middleware fyller ryggsekken, interruptors slipper videre eller svarer selv

Lag 5 · det brukeren ser

UI: liste, skjema og tilstand

Server-komponenter (RSC) kan kalle servicen direkte, fordi de kjører på serveren. Klient-komponenter må gå via en server action eller en fetch til en API-rute. Uansett kommer svaret tilbake i samme form: { ok, data } eller { ok: false, error }.

List-komponent

RSC som bruker service

Kjører på serveren, henter ctx.user fra requestInfo og kaller service.list. Ingen useEffect, ingen loading-state i klienten. Suspense viser en plassholder mens dataene kommer.

Create-komponent

Skjema med server action

useActionState gir deg forrige svar og isPending. Actionen sender ctx.user til samme service som API-ruta, fordi rute-interruptors ikke beskytter server actions.

Klient med fetch

project-api.ts + useTransition

fetch-kallet ligger i én fil. Komponenten får et Result tilbake og leser error.code. Cookien følger med automatisk når forespørselen går til samme domene.

Skjemaet

Form med inputfelter
Bruk <form> og name på feltene, så fungerer både FormData og tastatur (Enter sender).
Labels
Hvert felt har en <label htmlFor>. Skjermlesere leser den, og klikk på teksten fokuserer feltet.
ARIA
aria-invalid på feltet med feil, aria-describedby som peker på feilmeldingen, role="alert" så feilen blir lest opp.
Button
type="submit", deaktivert mens den jobber, og teksten forteller hva som skjer: «Lagrer...».
Placeholder
Et eksempel på hva som skal skrives. Aldri en erstatning for label, den forsvinner når brukeren skriver.

State

Formdata
La FormData lese verdiene ved submit. Feiler det, sender actionen verdiene tilbake (values), så feltet kan fylles inn igjen med defaultValue.
Pending
Loading / lagrer. Hindrer dobbel innsending og viser at noe skjer.
Success
Bekreft med role="status" og tøm eller lukk skjemaet.
Error 400
Validering. fieldErrors.title[0] vises ved feltet som er feil.
Error 401 / 403
Auth. 401: send til innlogging. 403: forklar at brukeren mangler tilgang.
Error 409
Duplikat. Si hva som allerede finnes.
Error 500
Serverfeil. Generell melding og mulighet for å prøve igjen.

Logikk ved submit

preventDefault
Bare når du sender med fetch selv. Med server action tar React seg av innsendingen.
Validering
Rask sjekk i klienten for god brukeropplevelse. Serveren validerer alltid på nytt, fordi klienten kan omgås.
Submit av data
Tre veier: server action, fetch til en API-rute, eller et vanlig <form method="post"> slik /login gjør. For prosjekter ender alle i samme service.

Rollen sjekkes tre steder, men bare to av dem er sikkerhet

Interruptor

requireAdmin på DELETE

Kjører på serveren før controlleren. Uten admin-rolle får brukeren 403, og servicen kalles aldri.

Service

canAccess: eier eller admin

Å lese og endre ett prosjekt krever at du eier det eller er admin. Gjelder uansett om kallet kommer fra API-ruta eller en server action.

UI-sjekk

Skjul Slett for andre

Brukervennlighet, ikke sikkerhet. En vanlig bruker kan fortsatt sende DELETE med curl eller fra DevTools, så serveren må alltid sjekke selv.

Context (AuthProvider) gir klient-komponenter tilgang til innlogget bruker uten å sende den som prop gjennom hvert nivå. Brukeren kommer fra serveren (ctx.user) og sendes inn i provideren i AppLayout. Konteksten er en kopi for visning. Det er serveren som bestemmer.
